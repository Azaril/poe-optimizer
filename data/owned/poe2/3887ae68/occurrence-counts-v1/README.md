# Requested counts on exact skill occurrences

This packet extends owned Import's usage transport to authored Direct skills and
skills supplied by an exact tree or item occurrence. Native Core/Data/Engine
contracts and every numerical program remain unchanged. Publication validation
is recorded in `runs/owned-occurrence-counts-07/validation.json` and the living
implementation plan. The eighteen-file package rebuilds byte-identically, adds
nine selected preferences (sixteen across all presets) and preserves the prior
drafts by inverse delta. Exact target/source checks and a real V3 schema revision
pass; an explicitly supplied stale policy is rejected. All five originals remain
Pending, so this checked import release is not whole-build numerical coverage.

The predecessor is `runs/owned-generated-preset-inputs-05/package`, input
`26b4ecd72e81fd40031e477aaa24a19ad0c4601afbc9f43e13101319bb801bfa`.
Six injected source rules cover manual Sand/Water Djinn, their exact Tree supplies,
and two already-reviewed Firebolt Item-name frames. No build file, selected
source ID, skill name or item name is embedded in native evaluation code.

All rows use existing Skill-target usage policy `326a`, RequiredOnce Integer
parameter `326b` (0 through 4), and requested Count stat `326c`. This is a reviewed
transport domain, not an assertion that all legal gameplay counts are bounded
by four. No definition, schema, slot, program, table, query or evaluation bundle
is added. The policy's existing historical Sniper program ID does not restrict
its generic Skill target; its separate reservation consumer is unchanged.

An explicit `groupCount` wins by presence, including zero. Otherwise, exactly one
reviewed source effect supplies `count`. Manual source groups admit only the
catalogue-checked support companions listed in `companion-evidence.json`; the
generated join retains its existing singleton-source frame. Missing, malformed,
fractional or out-of-domain counts remain Pending. Only generated rows admit
the explicit source spelling `count="nil"` as integer 1: pinned SkillsTab loading
and the complete generated-source witness demonstrate this value. It is an
offline source recipe, not native Lua truthiness or an evaluator default.

Raw quality and requested count have independent decoding. A proved generated
source with malformed quality may still carry a valid requested count; a stale,
ambiguous or missing provider cannot. Authored Direct requires an actually
absent source attribute. The historical raw-input adapter's acceptance of
`source=""` does not establish a retained manual occurrence in PoB.

The importer uses the shared exact provider resolver and existing parameter
recipes. Old physical usage policies retain their wire format and physical
inventory capability. The opt-in V3 policy appends typed preset preferences only
after historical normalization, preserving old issue allocation and raw-input
bindings. Generated bindings use exact-source applicability; manual bindings
are required by their supplying preset. Scenario overrides retain the existing
Core composition semantics.

This packet does **not** make requested count an actor-population or reservation
rule. Djinn have ordinary reservation, without the skeletal multiple-reservation
count consumer. Their demonstrated multiplicity consumer is Full DPS reporting.
Inclusion, generated activation, primary/secondary effect scope, actor/action
attribution and aggregate stacking still need their own owned consumers. Gameplay
usage inventories and complete-build numerical coverage remain Pending.

`source-facts.json` records pinned loader/count/consumer excerpts. The source
vectors authenticate primary-effect count observations in both byte-identical
generated-source reports (46 cases per JIT mode), separately from the new optional
Full DPS attribution witness. `companion-evidence.json` stores actual pinned
catalogue rows to prove that admitted siblings cannot supply the target effect.
These large source reports are optional publication evidence, never native
runtime inputs. Ordinary authoring checks use tracked files and the manifest.

Reproduction uses new output directories:

```text
cargo test -p poe-optimizer-cli --no-default-features --test owned_occurrence_counts_cli --locked
cargo test -p poe-optimizer-cli --no-default-features --test owned_occurrence_counts_cli occurrence_count_publication --locked -- --ignored --nocapture --test-threads=1
cargo test -p poe-optimizer-cli --no-default-features --test owned_generated_skill_inputs_native published_occurrence_counts --locked -- --ignored --nocapture --test-threads=1
```

For publication, set `POE_OPTIMIZER_TEST_OCCURRENCE_COUNT_PRIOR` to the exact
predecessor and `POE_OPTIMIZER_TEST_OCCURRENCE_COUNT_OUTPUT` to a new directory.
The native component reads the published parent through
`POE_OPTIMIZER_TEST_GENERATED_INPUT_OUTPUT`. Its explicit finite fixture supplies
unrelated closure; it tests the real count program on distinct Direct, Tree and
Item targets, not complete original-build mechanics.
