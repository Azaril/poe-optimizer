# Build generality review and checkpoint

**Reviewed and checkpoint accepted:** 2026-10-04. The owner approved adding this
checkpoint and continuing the five-build goal. It does not silently approve
unresolved public-model changes or certify complete builds.

## Assessment

The owned architecture is substantially data-driven. The reviewed Core/Engine,
Import/Data and search paths contain no production dispatch by original-build,
spell or item name. Exact definition IDs, coefficients, source adapters and
family-specific authoring packets are legitimate data. Native execution uses
injected typed rules, exact occurrences and one preparation/execution graph.
Generic search separates its algorithm from candidate domains.

Generality is not established end to end: all five original builds remain
incomplete natively. Some contracts support only their first demonstrated
mechanic shape, and production search still uses the optional PoB XML catalog
adapter. Structural limits and unfinished integration are the principal risks.

## Checkpoint gates

Run alongside D1-D5, before extending a shared public contract and at original
build integration checkpoints. This does not require implementing every mechanic
before completing the closest build. Finish the in-progress permanent-reward
slice using existing APIs; then prefer integration that exercises shared receiving
and action contracts over unrelated isolated producer families.

1. [x] Review production contracts, their fixtures and default dependencies.
   Separate observed capacity limits from incorrect results.
2. [ ] For each shared contract being extended, select two structurally different
   real mechanic cases. Relevant axes include authored/generated sources,
   repeated sources/recipients, item-local/actor-wide effects and distinct action
   or stat-set selections. A simple coefficient change need not cover unrelated
   axes. Record unsupported cases explicitly.
3. [ ] Prove data-only extension for definitions/coefficients within existing
   semantics. Test identity independence with renamed/reordered definitions and
   repeated occurrences. Genuinely new operations receive a versioned domain
   extension, not a named skill branch or a second build model.
4. [ ] Pair finite component proofs with unchanged imported requests. Report the
   actual blocker for all five saved selections and all 110 queries. Complete
   build success requires real admission, providers, contributors, scenario and
   final metrics; fixture-supplied closure cannot certify it.
5. [ ] Add a small independent holdout corpus chosen by mechanism intersections,
   with provenance and pinned reference outputs. Keep development, mutation and
   held-out cases distinct. Expand whole-build holdout parity after the first
   usable originals; controlled edits are not independent holdouts.
6. [ ] Define and run a reproducible CI integration subset, including explicit
   setup for required ignored tests, with broader slower validation separately.
   Keep native component checks independent of optional PoB execution.
7. [ ] Before completing D4, demonstrate owned candidate mutation, locks,
   legality, exact objectives and fixed-scenario native evaluation. Then expand
   joint search and measure real preparation/reuse and Rayon throughput.

Each receipt names the subsystem, contrasting cases, data/contract delta,
unchanged-original outcomes, next blocker and any retained legacy consumer.
The living implementation plan remains the sole active resume point.

The subsequent [retirement audit](legacy-retirement.md) identifies the unused
equipment/Mace Import closure for removal, distinguishes shared resistance laws
from legacy application adapters and owned schema history, and adds the owner's
Lua behavior/type cleanup gate. Follow that existing debt inventory rather than
creating another parallel cleanup plan.

## Owner decisions and remaining reviews

- **Accepted 2026-10-04:** [generated usage](owned-generated-skill-usage-proposal.md)
  stays on skill presets with exact-source applicability. This grants no
  activation/provider authority; versioned representation and validation remain
  implementation work.
- **Accepted 2026-10-04:** [separate socket configurations](owned-socket-configurations.md),
  distinct from rolled item descriptors and physical copies. The API/migration
  details and native receiving semantics remain implementation work.
- **Required:** deterministic native evaluation and repeatable oracle execution.
  On 2026-10-05 the owner classified the demonstrated Frost lifecycle discrepancy
  as a PoB bug, excluded that affected comparison and requested independent
  stability validation for the other builds. The proposed rebuilt canonical
  protocol was not adopted. Never retry until outputs happen to agree.
- Physical-field classification, expanded source-property ownership and scoped
  coverage need concrete reviewed contracts before changing current authority
  or completeness rules. This checkpoint authorizes investigation, not relaxed
  gates.

Older source-interpreter proposals are historical wherever they conflict with
the accepted [domain architecture](domain-architecture.md). DSL/authoring
investigation stays within that boundary.
