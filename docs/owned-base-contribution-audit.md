# BASE contribution audit

The retained source evidence does not support publishing the six BASE memberships
with arbitrary native ranks. The audit exposes item-copy contributions after
passives, unsupported equipment destinations in the current ordered binder, and
order-sensitive values inside the declared native input domain. These are concrete
next design obligations, not permission to omit item donors.

This audit changes no release, public contract or rule closure. Its numerical
evidence is pinned to `runs/owned-attribute-increase-01/package`, input
`29e4e9ef2b321bb6c802d9970666e8bf85afb805830ca9c2bbfc03bceaafb1ef`.
Six INC memberships are Complete; BASE memberships, the global query inventory and
complete build evaluation remain open. Complete original builds remain **0/5**.
The living implementation plan identifies the latest integration package;
retaining this proof snapshot does not create a separate runtime mode.

## Source transport and owned gaps

Pinned `Item.lua:2764–2777` constructs enchant, rune, class-requirement, implicit and
explicit groups in that order. Slot preparation filters their copies while
preserving surviving order. Existing owned normalization already requires a
reviewed complete member/order proof before assigning `modifier_order`; retain
that boundary rather than sorting saved text lines.

`CalcSetup.lua:1473–1530` can combine Focus or corrupted-jewel modifiers before
scaling. Its quiver/amulet copy pass follows passive merging at `1651–1667`.
The later non-Amulet slot pass in `CalcPerform.lua:1489–1534` groups matching
numeric BASE/INC modifiers before scaling. Per-line scaling followed by summation
does not generally reproduce that grouped operation. The source's `pairs` traversal
is not an authored game order.

Current modifier owners `295c`, `2974`, `298c`, `29a4` are admitted structurally by
all 1,756 item templates. Their equipment-use programs are not restricted to
character slots. Provider discovery includes passive sockets and item sockets,
but `ContributionOrigin::ItemModifier` currently accepts only character-slot
destinations. A character-slot-only membership cannot claim the whole current
donor domain. Parent-item jewels and passive jewels need reviewed treatment;
source UI traversal places parent jewels after their parent and passive sockets
afterward in node-ID order, which is evidence to assess rather than a native
runtime representation to copy.

Source import admission is independently incomplete. The current item-member
policy admits eleven recipes, none of the four attribute recipes. Useful converted
attribute members therefore do not establish a complete item inventory/order.
Unconverted or inactive alternatives must remain explicit obligations.

## Numerical counterexamples

Integral per-occurrence values do not make arbitrary binary64 summation exact.
For `x = 9,007,199,254,740,000`, a left fold starting at 7 gives 8 for
`[x, x, -x, -x]` and 7 for `[x, -x, x, -x]`. Each donor and both final results fit
the Integer domain. The native component test uses the current catalyst,
effective-amount, Count projection and attribute receiver programs with values
inside the current declared signed/scaled ranges. These direct facts prove a
declared-domain issue; they do not establish gameplay obtainability or import
admission for such an item.

A positive passive suffix can have a conditional final-output argument under
additional bounds. It does not prove equal BASE subtotals, and the observed later
copy lane means passives are not universally the final suffix. The arithmetic
counterexample permutes `[3, 5, 25]` after a large prefix, obtaining different
out-of-range subtotals; a later signed contribution exposes them as 1024 and 1028.
Clamping, rounding and INC scaling need their own final-output evidence. Neither
configurable resource limits nor successful small original-build values establish
the required candidate-wide bounds.

## Validation and next actions

The test target is `owned_attribute_base_audit` in `poe-optimizer-cli`:

- `authored_base_source_inventory_retains_every_observed_lane` checks the retained
  corpus and checked-in pins without a vendor checkout or local reports.
- `numeric::integral_donors_do_not_authorize_reordering_signed_base_contributions`
  and `numeric::positive_suffix_permutations_do_not_prove_base_subtotal_equality`
  check the explicit arithmetic counterexamples.
- Ignored `retained_base_source_reports_match_exact_projection_in_both_jit_modes`
  authenticates the retained reports and pinned optional source.
- Ignored `numeric::current_item_programs_and_attribute_receiver_reproduce_numeric_order_limits`
  reads `POE_OPTIMIZER_TEST_ATTRIBUTE_BASE_RELEASE` and exercises unchanged native
  component programs, preserving the supplied release inventory and closures.

All three default tests pass (0.02s); both optional retained-source and current
native-program checks pass (3.13s on the final rerun). Logs are retained as
`runs/owned-attribute-base-audit-default-02.log` and
`runs/owned-attribute-base-audit-retained-native-02.log`. This does not claim a
new Lua execution. The living [implementation plan](implementation.md) records
the remaining checkpoint checks and next implementation work.
